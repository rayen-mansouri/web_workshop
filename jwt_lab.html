What the server does with your token, step by step

    

      
1
Split the token into 3 parts at the . dots
·

      
2
Read the header to decide which algorithm to verify with
·

      
3
Re-sign header.payload with the server's secret and compare to the signature
·

      
4
If the signatures match → trust the payload. If not → reject with 401.
·

    

  


  

    
What the server does, in the order it does it

    

      
1
Token arrives in the Authorization: Bearer … header. Nothing inside it is trusted yet.

      

      
2
The server re-computes the signature from the header, the payload and its own secret.

      

      
3
If you changed even one character of the payload, the recomputed signature changes completely — mismatch.

      

      
4
Reject: 401 Unauthorized. The signature is the entire security of a JWT — and the whole reason the attacks below exist.

    

  







  
Step 3 — what the signature is supposed to do

  
HMAC vs RSA — two ways to sign

  
The signature is a keyed hash over header.payload. With HS256 the same
  secret both signs and verifies — so it must never leave the server. With RS256 a private key signs
  and a public key verifies — that public key can be shared freely. Each design has a different
  attack.


  

    

      
✓ HS256 — shared secret

      
    
        
  • One secret s3cr3t signs and verifies.
    • 
        
  • If it leaks → attacker can forge any token.
    • 
        
  • If it's weak → attacker can brute-force it offline.
    • 
      

    

    

      
⚠ RS256 — public / private

      
    
        
  • Private key signs, public key verifies.
    • 
        
  • Public key is, by design, public.
    • 
        
  • If the server trusts the header's alg → attacker swaps RS256 for HS256 and uses the public key as the HMAC secret.
    • 
      

    

  


  
That's also why step 2's toggle matters. The signature is only
  useful if the server actually checks it, and if it checks it with the right algorithm. Every
  attack in the next few steps breaks one of those two assumptions.







  
Step 4 — attack 1: "alg": "none"

  
Tell the server not to check

  
The header itself names the algorithm. If the server blindly trusts it, you can set
  "alg":"none" and strip the signature entirely. Any payload you want, no key required.


  

    
tampered header

    
{ "alg":"none", "typ":"JWT" }

    
tampered payload

    
{ "sub":"7", "name":"alice", "role":"admin" }

    
signature

    
(empty)

The fix: the server must pin the
  algorithm it expects — jwt.verify(token, secret, { algorithms: ["HS256"] }) — and reject
  none outright. Never let the token's own header pick the algorithm.







  
Step 5 — attack 2: algorithm confusion

  
Public key in. Forged token out.

  
With RS256 the public key is, by definition, public. If the server trusts the header's
  alg, you change it from RS256 to HS256 — and sign with the
  public key you already have as if it were an HMAC secret. The server does the same thing, gets the
  same result, and lets you in.

Why it works — the same bytes, two meanings

    

      
🔑public.pem
(was a verifier)

      

      
🧮HMAC-SHA256
(attacker's secret)

    

    
The public key is a public string. HMAC takes a string. Same string, different meaning.

  


  
The fix: pin the expected algorithm on
  the server. Never let the token's header choose it. If you publish RS256, verify only RS256.







  
Step 6 — attack 3: the weak secret

  
If the secret is a dictionary word, you already have it

  
HS256 tokens are offline-verifiable: anyone holding a valid token can try candidate
  secrets locally, with no rate limit. A short, human-memorable secret is the most common JWT weakness in the
  wild. Watch the wordlist below try — each attempt is local, silent, and instantaneous.


  

    
    
  

  

  


  
The fix: a long, random secret (32+
  bytes of entropy) — never a word, never a project name, never secret. And rotate it on a
  schedule.







  
Step 7 — more ways in

  
Same idea, different disguise

  
The header is more than alg. Every field in it is attacker-controlled and
  often trusted. Here are four more surfaces, and what each one lets you do.


  

    
Attack surfaces in a JWT

    

      
🧩 alg: none

        
"alg":"none"

        
If the library accepts it, no signature check happens at all. See Step 4.

      
🔀 alg confusion

        
RS256 → HS256

        
Use the public key as an HMAC secret. See Step 5.

      
🪝 kid injection

        
"kid":"../../etc/passwd"

        
If kid is used to pick a key file, point it at a path you control — or a known file whose first bytes you can predict.

      
🌐 jku / x5u

        
"jku":"https://evil/keys.json"

        
If the server fetches the keyset from a URL you supply, host your own keys and sign with them.

      
📭 empty signature

        
header.payload.

        
Some parsers treat a trailing dot as "signature optional". A trailing empty signature must always be rejected.

      
🕳️ null byte / padding

        
role="admin\u0000"

        
Some JSON parsers truncate on NUL or on trailing spaces — a value that "isn't admin" during the check can be admin after the parse.

A realistic chain

    

      
1. The app issues HS256 tokens. The secret is secret — found by offline brute-force in under a second.

      
2. The attacker forges a token with "role":"admin", signed with that secret.

      
3. They call /api/admin/users — the server sees role admin and hands back every user record.

      
4. They call PATCH /api/users/1 with a new email, hit "forgot password", and take over the real admin account.

    

  


  
Ask yourself every time: what claims does the server trust, and what did it do to make
  sure those claims are the ones it issued?
