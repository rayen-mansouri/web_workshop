SSRF — Server-Side Request Forgery

A deep-dive, step-by-step interactive lab. Watch exactly how an attacker tricks a trusted server into making requests on their behalf.

Step 1 — The Core Vulnerability

How a server becomes your proxy

Many apps fetch URLs for you: image imports, link previews, webhooks, PDF generators. The server makes that request from inside its own network, where it is trusted. If you control the URL, you control where the server sends its requests. Watch the sequence below.

Network Topology
1. Normal Feature: You paste an image URL. app.com downloads it from images.com and shows it to you.
2. Direct Attack Blocked: You try to open the internal admin panel yourself. The firewall only lets machines inside the private network reach it, so you are stopped.
3. The Server as Proxy: You give app.com the URL of the internal panel instead. app.com is inside the network, so the firewall trusts it. It fetches the page and hands it to you.
Step 2 — What the Attacker Steals

The prize: cloud credentials

The most famous SSRF target is the cloud metadata service at 169.254.169.254. It is reachable only from the server itself and hands out its cloud credentials. Unlike CSRF, the attacker often can read the response. (If the app hides the response, it is called blind SSRF: the request still happens, only the output is hidden.)

Idle
1. The Payload: The attacker types the metadata address into the import box and clicks Fetch.
2. The Trusted Request: app.com sends the request from its own machine. The metadata service sees an internal caller and answers.
3. The Leak: app.com returns the fetched content to the attacker, including the role credentials. With those, the attacker can act as the server in the cloud.
Step 3 — Defense 1: Validate the URL

Check where the URL really points

Before fetching, the app must decide if the destination is allowed. Best practice: allowlist the domains you need, allow only http(s), then resolve the domain to an IP and reject private, loopback and link-local addresses. Checking the name alone is not enough, because an attacker can point their own domain at an internal IP.

URL Validation
1. Safe URL: The app receives images.com/cat.jpg and looks up its IP address: a public one.
2. Allowed: The check passes, so the app fetches the image.
3. Malicious URL: evil.com looks harmless, but its DNS record points to 10.0.0.5, a private address. The IP check refuses it. Also disable or re-validate redirects.
Step 4 — Defense 2: Network Controls

The network says "No"

Validation can have bugs, so add a second layer. An egress firewall stops the server from reaching internal services and the metadata address at all. On AWS, IMDSv2 also requires a special header token that a simple SSRF cannot add. Even if the attacker bypasses the URL check, the request dies on the network.

The Egress Firewall
Waiting to fire request...
1. The Trigger: A bypass tricks the URL check. app.com tries to fetch the metadata address.
2. The Block: The request leaves the app, but the egress firewall has a rule denying that destination.
3. The Rejection: Nothing reaches the metadata service. app.com gets a timeout or error, and the attacker gets nothing.
