IDOR — Insecure Direct Object Reference

A hands-on walkthrough. No quotes, no semicolons, no code — just a different number. You will watch a single changed digit hand back somebody else's data, live, in your browser. Everything below is simulated.

Where does your typing go?

You are logged in as alice. The page shows your invoice with a link that ends in a number — the invoice's id. Below is exactly what the backend does with that number: it drops it straight into a database query. Look at what it does not do.

Step 2 — your first real payload

Change one digit. Read someone else's invoice.

There is no special syntax here. No quotes, no OR 1=1, no <script>. An IDOR payload is simply a different valid id. The app trusts that the number you sent is a number you are allowed to see — and nothing more.

1041
Your own invoice is 1042. This one is 1041 — one digit lower, and it belongs to a different customer. The server looks up whatever id you name and hands the row back, because the query never asks "does this row belong to the person asking?"

What happens, step by step
1
Your browser is logged in as alice — the session cookie says "I am user 7".
2
The link carries a raw record id: /invoice?id=1042. The server reads that number straight out of the URL.
3
The query is WHERE id = 1042 — by id alone. Nothing compares the row's owner to your session.
4
Change 1042 → 1041 and the exact same query returns a different person's invoice. The server never noticed anything unusual.
Step 3 — the check that isn't there

Authentication ≠ authorization

The server did check that you're logged in. That's authentication. What it never did was check whether this specific record belongs to you — that's authorization. IDOR is almost always that second check going missing.

❌ What the app does
SELECT * FROM invoices
WHERE id = 1041;
request
id=1041
⛓️no check
Bob's invoice
✅ What it should do
SELECT * FROM invoices
WHERE id = 1041
  AND owner_id = 7;
request
id=1041
🔒owner check
Bob's invoice

The one-line fix: every query that fetches an object by id must also filter by the owner taken from the session — never from the request. If the row comes back empty, answer 404 (not 403, which still tells the attacker the record exists).

Step 4 — object references aren't all numbers

Same flaw, different disguise

"Direct object reference" means whatever the app uses to name a thing: a number, a UUID, a filename, a hidden form field. The flaw is the same in every case — the app lets you supply the reference and never checks that it's yours. Making the reference harder to guess does not fix it.

Six ways a record can be named
🔢 Sequential ids
?id=1041
The easiest to walk. Every customer sits one number away from the next.
🆔 UUIDs
?id=550e8400-e29b-…
Hard to guess — but they leak constantly in emails, API responses, JS bundles and referrer headers. Unguessable is not the same as unauthorized.
🔐 Encoded ids
?id=MTA0MQ==
That's just base64 for 1041. Encoding is not a security control — decode, change, re-encode.
📝 Hidden form fields
<input type="hidden" name="user_id" value="7">
Anything the browser sends can be edited. Hidden just means "not displayed".
🔁 HTTP method
PATCH /api/users/8
Developers protect GET and forget PUT, PATCH and DELETE — writes are where the real damage is.
📁 File names
?file=invoice_1041.pdf
Filenames and paths are object references too, and often the only thing standing between you and someone's documents.

That's also why attackers start by looking at what the app already sends them — their own profile URL, their own invoice id, their own API responses — to learn the naming scheme before touching anything else.

Step 6 — horizontal vs vertical

Two directions you can break out in

Horizontal means staying at your own privilege level and reading another user's data — Bob's invoices, Carol's messages. Vertical means climbing to a higher privilege level — a normal user reaching admin-only records or actions. Both are IDOR; both come from the same missing check.

Step 7 — at scale

Why nobody needs to be clever about this

A script doesn't need to be smart. Sequential ids mean an attacker can just walk the range and collect whatever comes back. Every request in this sweep returns 200 OK with somebody's data — there is no point at which the server says "that one isn't yours".

Step 8 — why this is a big deal

It's never just "one extra invoice"

Reading one other invoice proves the check is missing. In a real attack, the same flaw means every record in that table — and, once the id shows up on a write endpoint, it means changing somebody else's account.

One number → every record → account takeover

A realistic chain
1. PATCH /api/users/8 accepts a new email for user 8 — and never checks that you are user 8.
2. The attacker sets user 8's email to their own address. No password needed.
3. They hit "forgot password" on the login page with that email.
4. The reset link lands in the attacker's inbox. They now own the account — and if user 8 was an admin, they own the app.

Ask yourself every time: what is the app using to name this thing, who supplies it, and does the server verify it belongs to the person asking?
