01 / INTRO
Why web exploitation?

Three generations, same battlefield.

From static pages to social apps to AI — the web has stayed the biggest attack surface.

Massive scale

~1.49 billion websites exist. ~217 million active. An estimated 30,000 get hacked every day.

Many motives, one door

Hacktivists, ransomware groups, and attention seekers all come in through the web — the widest door there is.

Always relevant

Unsupervised vibe-coding made an ever bigger attack surface. The fundamentals stay the same.

02 / INTRO
Its relevance

Your starting point.

  • Entry point: to get your way into any system, web exploitation will be your starting point.
  • Bug bounty: web exploitation is the lowest barrier to get paid — most programs are web-focused.
  • Relevant then, even more now: unsupervised vibe-coding made an ever bigger attacking surface.

    • Key idea: understanding attacker behavior helps build stronger defenses. Every bug today comes from trusting input the user controls.

    06 / FUNDAMENTALS
    Fundamentals

    Client-side vs server-side.

    Client Side

    Everything that runs in the user's browser on their device.

    • HTML, CSS, JavaScript
    • Handles UI & interactions
    • Instant feedback for the user

    Server Side

    Everything that runs on the server, behind the scenes.

    • Server logic, APIs, databases
    • Handles security & data processing
    • Stores, updates & manages data
    BrowserCLIENT
    ServerLOGIC
    DatabaseSTORAGE

    Request in → logic runs → response out. Every vulnerability lives somewhere on this path.

    08 / FUNDAMENTALS
    Sessions

    How cookies work.

    A cookie is a note the server asks your browser to keep — and hand back on every request. This is why IDOR and XSS-cookie-theft exist.

    BrowserYOU
    ServerAPP

    1. Log in → 2. Server creates session → 3. Set-Cookie header → 4. Browser stores → 5. Sent automatically on every request

    Set-Cookie: session_id=8f2a91c4; HttpOnly; Secure

    HttpOnly means client-side JavaScript can never read the cookie — a direct defense against cookie theft via XSS. No ownership check on the server side is exactly how IDOR slips through.

    Section 01
    INJECTIONS

    Untrusted input reaches an interpreter — a database, a shell, or the browser — and changes what it does.

    XSS SQLi CMDi
    INJECTIONS · 01
    XSS · Where & impact

    Cross-Site Scripting.

    Reflected

    Fires once via a crafted link. Input is echoed back immediately.

    Stored

    Saved on the server, fires for every visitor. Most dangerous.

    DOM-based

    Entirely client-side JavaScript mistake — never touches the server.

    WHERE IT'S FOUND

    • Comment fields, profile names, search boxes — anything echoed back.
    • URL parameters rendered into the page without encoding.
    • Anywhere user input lands in HTML/JS context unescaped.

    IMPACT

    • Session hijacking via cookie theft · account takeover
    • Defacement · phishing · keylogging in the victim's browser
    • Actions performed as the victim — CSRF-like behavior
    INJECTIONS · 01
    XSS · How it works

    The attack flow.

    Why it works: the server echoes input without encoding it. The browser has no way to tell this script from the site's own code — so it runs with full trust.

    INJECTIONS · 01
    Hands-on lab

    Break XSS.

    1. Open Lab 1 — Reflected XSS and click "Access the lab"
    2. Type <script>alert(1)</script> into the search box and submit — it fires immediately, in your own browser only
    3. Open Lab 2 — Stored XSS and click "Access the lab"
    4. Open any blog post, post the same payload as a comment (name/email/website can be anything)
    5. Go back to the blog list and reopen that post — the alert fires again, with no form resubmission: that's the difference between reflected and stored
    Target

    PortSwigger's hosted search box and blog comments

    Goal

    get your script to execute in another visitor's browser

    Observe

    An alert firing on page load, with no form resubmission, confirms stored XSS rather than just reflected.

    INJECTIONS · 02
    SQL Injection · Where & impact

    SQL Injection.

    Untrusted input reaches a database query unescaped — letting an attacker change what the query actually does.

    WHERE IT'S FOUND

    • Login forms, search boxes, URL filters — any input used in a query.
    • Numeric and string parameters alike, including hidden form fields.
    • Behind APIs where the app builds SQL by string concatenation.

    IMPACT

    • Authentication bypass — log in as admin with ' OR '1'='1
    • Full database dump — usernames, password hashes, PII
    • Data modification or deletion — sometimes RCE via INTO OUTFILE
    INJECTIONS · 02
    SQL Injection · How it works

    The query break.

    Why it works: the quote closes the string literal early. Everything after becomes real SQL, and -- comments out the rest. One character bypassed the login system.

    INJECTIONS · 02
    Hands-on lab

    Break SQLi.

    1. Open Lab 1 — Retrieving hidden data and click "Access the lab" (free account, opens instantly)
    2. On the shop page, pick a category — the URL shows ?category=Gifts
    3. Change the URL to ?category=Gifts'+OR+1=1-- and hit enter — every product appears, including unreleased ones
    4. Open Lab 2 — Login bypass and click "Access the lab"
    5. On the login form, enter administrator'-- as the username and anything as the password — you're logged in as admin, no password needed
    Target

    PortSwigger's hosted lab — opens in your browser, no setup

    Goal

    extract hidden data, then bypass a login entirely

    Observe

    Products that shouldn't be visible, or a successful admin login with zero valid credentials, confirms SQL injection.

    INJECTIONS · 03
    Command Injection · Where & impact

    Command Injection.

    User input flows into a system command — like ping, nslookup, or a file convert — and the shell executes whatever the attacker appends.

    WHERE IT'S FOUND

    • Diagnostic tools — ping, traceroute, DNS lookup from the UI.
    • File converters, image processors, PDF generators.
    • Backup / export features that shell out to system commands.

    IMPACT

    • Full server compromise — read files, run processes, pivot.
    • Often the highest-severity bug you can find — RCE.
    • Chained with SSRF or uploads, it's game over for the host.
    INJECTIONS · 03
    Command Injection · How it works

    The shell break.

    Why it works: the app calls system(), exec(), or shell_exec() with user input. Shell metacharacters (; | && $()) chain extra commands. The OS runs them with the web server's privileges.

    INJECTIONS · 03
    Hands-on lab

    Break CMDi.

    1. Open Lab 1 — OS command injection, simple case and click "Access the lab"
    2. Pick any product, click Check stock, and resend that request in Burp — note the storeId parameter
    3. Change it to storeId=1|whoami and resend — the command's output comes back inside the stock response
    4. Open Lab 2 — Blind OS command injection with time delays for the harder, no-output variant
    5. In the feedback form's email field, submit something like ||ping+-c+10+127.0.0.1|| — a response that now reliably takes 10 seconds longer confirms execution with nothing ever shown
    Target

    PortSwigger's hosted stock-checker and feedback form

    Goal

    get the server to run an OS command of your choosing

    Observe

    A command's output appearing where only a number was expected — or a response that's consistently 10 seconds slower — confirms OS command injection.

    Section 02
    BROKEN TRUST

    The app trusts something it shouldn't — an ID, a token, or a login with no rate limit.

    IDOR JWT Brute-force
    BROKEN TRUST · 01
    IDOR · Where & impact

    Insecure Direct Object References.

    The app exposes an internal ID and lets you swap it to access another user's object — without checking you own it.

    WHERE IT'S FOUND

    • URLs like /invoice/1001 or /user/42
    • API calls with sequential IDs in body or query params.
    • Hidden form fields carrying the object ID.

    IMPACT

    • Read other users' invoices, orders, messages, PII.
    • Modify or delete another account's data.
    • A broken access control bug — not code execution, but often critical.
    BROKEN TRUST · 01
    IDOR · How it works

    The ID swap.

    Why it works: the server fetches whatever ID is in the URL. It checks that you're logged in — but never that invoice 1002 actually belongs to you. Multiply by every ID and the whole table is exposed.

    BROKEN TRUST · 01
    Hands-on lab

    Break IDOR.

    1. Open the lab link and click "Access the lab"
    2. Log in with the credentials the lab gives you (wiener:peter) and open My account
    3. Look at the URL — it ends in ?id=wiener
    4. Change it to ?id=carlos and reload — Carlos's account page loads, API key and all, with no login as Carlos ever happening
    Target

    PortSwigger's hosted account page

    Goal

    read another user's private data by editing an ID

    Observe

    A 200 response containing another account's data — instead of a 403/404 — confirms IDOR.

    Demonstrative labOpen IDOR LabLabUser ID controlled by request parameterReadingPortSwigger — Access control / IDOR
    Zero installJust a browserPortSwigger Academy
    BROKEN TRUST · 02
    JWT Attacks · Where & impact

    JSON Web Token attacks.

    JWTs carry identity in three base64 parts: header.payload.signature. If the signature is weak, missing, or checked badly, you can edit the payload — like "role":"admin" — and the server believes it.

    WHERE IT'S FOUND

    • alg: none — server accepts unsigned tokens.
    • Weak HMAC secret — brute-force the signing key.
    • Algorithm confusion — RSA public key used as HMAC secret.

    IMPACT

    • Privilege escalation — become admin by editing one claim.
    • Account takeover — forge tokens for any user ID.
    • Bypass auth entirely if none is accepted.
    BROKEN TRUST · 02
    JWT Attacks · How it works

    The forged token.

    Why it works: the client controls every byte of the JWT. If the server doesn't strictly verify the signature (or accepts none), the payload is just base64 — editable in a browser.

    BROKEN TRUST · 02
    Hands-on lab

    Break JWT.

    1. Open Lab 1 — JWT authentication bypass via unverified signature and click "Access the lab"
    2. Log in with wiener:peter, capture the session cookie, and decode it (jwt.io or Burp's JSON Web Token tab) to see the header and payload in plain text
    3. Change the payload's sub claim to administrator, set the header's alg to none, and keep only the two base64 segments with a trailing dot — no signature at all
    4. Send that token as your session cookie to /admin — you're in as administrator, with nothing ever signed
    5. Open Lab 2 — JWT authentication bypass via weak signing key for the harder variant: crack the short HS256 secret offline with hashcat/jwt_tool against a wordlist, then re-sign a forged token using the real secret
    Target

    PortSwigger's hosted JWT session app

    Goal

    forge a token that logs you in as administrator

    Observe

    Access to /admin with a token you hand-edited — or one you re-signed after cracking the secret — confirms the server never properly re-verified before trusting the claims.

    BROKEN TRUST · 03
    Brute-force & Fuzzing · Where & impact

    Brute-force attacks.

    An attacker automates login attempts — guessing passwords, stuffing leaked credentials, or spraying common ones — because nothing stops the volume.

    WHERE IT'S FOUND

    • Login forms without rate-limiting or account lockout.
    • Password reset endpoints with guessable tokens.
    • API auth with no CAPTCHA or MFA.

    IMPACT

    • Account takeover at scale — no exploit needed beyond patience.
    • Credential stuffing spreads across sites (people reuse passwords).
    • With leaked wordlists, success is often just a matter of time.
    BROKEN TRUST · 03
    Brute-force · How it works

    The number game.

    Why it works: with no rate-limiting or lockout, the server happily accepts thousands of guesses per second. A CAPTCHA once per failure — or MFA — breaks the loop instantly.

    BROKEN TRUST · 03
    Hands-on lab

    Break Brute-force.

    1. Open the lab link and click "Access the lab" — grab the username and password wordlists linked in the lab's own description
    2. In your own browser, log in with an obviously wrong username/password and note the error text exactly
    3. Try a few candidate usernames from the wordlist, each with a wrong password — one returns a subtly different error ("Incorrect password" vs "Invalid username") — that's your valid username
    4. Point Burp Intruder at the login request, mark only the password field as the payload, load the password wordlist, and run the attack
    5. Sort results by response length or status code — the one row that differs from the rest is the correct password
    Target

    PortSwigger's hosted login lab

    Goal

    enumerate a real username, then brute-force its password

    Observe

    A wording difference between "bad username" and "bad password" is the leak; a shorter/different response during the password run is the hit.

    Section 03
    ABUSE OF AUTHORITY

    The browser or server has authority — and an attacker makes it act against the user's interest.

    CSRF SSRF
    ABUSE · 01
    CSRF · Where & impact

    Cross-Site Request Forgery.

    The victim's browser is tricked into sending an authenticated request to a site where they're logged in. The server sees a valid session cookie — and does what the request says.

    WHERE IT'S FOUND

    • State-changing actions with no CSRF token — transfer money, change email, delete account.
    • Cookie-based auth with SameSite=None or no SameSite at all.
    • GET requests that mutate data (the worst offender).

    IMPACT

    • Unauthorized actions performed as the victim — money transfers, email changes, posts.
    • Account lockout / takeover via email or password change.
    • Chained with XSS or stored data, it becomes stealthy and viral.
    ABUSE · 01
    CSRF · How it works

    The forged request.

    Why it works: the browser automatically attaches cookies to any request to the target site — regardless of which page caused it. The server can't tell the difference between a real transfer and this forged one unless it checks a CSRF token.

    ABUSE · 01
    Hands-on lab

    Break CSRF.

    1. Open Lab 1 — CSRF vulnerability with no defenses and click "Access the lab"
    2. Log in, go to My account, change your email once, and capture that request in Burp
    3. Right-click it → Engagement tools → Generate CSRF PoC, then open the generated HTML yourself — submitting it changes the email, with no token involved at all
    4. Open Lab 2 — CSRF where token validation depends on token being present for the trickier variant
    5. Repeat the same captured request but delete the csrf parameter entirely (not just blank it) before resending — the server accepts it anyway, because it only checks that some value exists, not that it's correct
    Target

    PortSwigger's hosted "my account" email-change feature

    Goal

    change another user's email without their involvement

    Observe

    An email that changes from a page the victim never meant to submit anything on — or a request that still succeeds once the csrf parameter is simply removed — confirms the token isn't actually being enforced.

    Demonstrative labOpen CSRF LabLab 1CSRF vulnerability with no defensesLab 2Token validation depends on token being presentReadingPortSwigger — CSRF
    Zero installBurp CSRF PoC generatorPortSwigger Academy
    ABUSE · 02
    SSRF · Where & impact

    Server-Side Request Forgery.

    The app fetches a URL on the attacker's behalf — the attacker makes the server issue the request, not the browser.

    WHERE IT'S FOUND

    • URL-fetching features — image/avatar import, PDF generation, webhook testers.
    • URL previews in chat apps — Slack, Discord, Telegram.
    • Any parameter that takes a URL and the server requests it.

    IMPACT

    • Reach internal services the attacker can't touch — admin panels, DBs.
    • Cloud metadata theft — 169.254.169.254 — often yields credentials.
    • Port scanning the internal network, pivot to other hosts.
    ABUSE · 02
    SSRF · How it works

    The inside job.

    Why it works: the request is made from the server itself — so it sails straight past firewalls that only block outside traffic. Internal services assume the request is legitimate because it came from inside.

    ABUSE · 02
    Hands-on lab

    Break SSRF.

    1. Open the lab link and click "Access the lab"
    2. Pick any product and click Check stock — this sends a request with a stockApi parameter holding a URL
    3. Intercept that request (Burp Proxy) or just resend it with the parameter changed to stockApi=http://localhost/admin — the internal admin page comes back through the public feature
    4. Change it again to stockApi=http://localhost/admin/delete?username=carlos and send it — the server deletes the user, acting entirely from inside its own network
    Target

    PortSwigger's hosted "check stock" feature

    Goal

    get the server to fetch an internal admin URL on your behalf

    Observe

    The admin interface's HTML appearing inside a "check stock" response — from a feature that was only ever supposed to return a number — confirms SSRF.
