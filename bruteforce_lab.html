Brute Force

A hands-on walkthrough. No clever payload, no syntax tricks — just a computer trying one guess after another, very fast, until something works. Everything below is simulated; nothing here touches a real login.

Step 1 — the code behind the login form

What happens when you hit "sign in"

Every login form is a yes/no oracle. You send a username and a password; the server compares the password to a stored hash and answers 200 OK or 401 Unauthorized. There is no concept of "how many times" — only "correct" or "incorrect". A script can ask the same question millions of times.

// simplified login handler
POST /login
{ "user": alice, "pass": hunter2 }

if (bcrypt.compare(pass, stored_hash[user])) → 200 OK
else                                             → 401 Unauthorized

A human types one password, waits, maybe tries again. A script sends the whole dictionary of possibilities in the time it takes you to blink. The form doesn't care — it just keeps answering.

Step 3 — the math of "search space"

Why length beats complexity

Every password lives in a search space — every string an attacker might have to try. That space grows exponentially with length: each extra character multiplies it by the size of the alphabet. Change anything below and every number on this panel recalculates live.

Just 2 extra characters (×3,843) beats adding the whole symbol set (×30) by over a hundred times. Length is where the exponential lives — complexity only gives you a one-time bump.

That's why security people say "length beats complexity." Going from 8 to 12 characters multiplies the search space by 62⁴ ≈ 14.7 million. Adding uppercase, symbols, digits — all of it together — doesn't come close.

Step 4 — four ways to guess

Same idea, different dictionaries

"Brute force" is the general name, but the candidate list matters enormously. A dictionary attack is not the same as enumerating every string — and credential stuffing is not guessing at all.

The four approaches, from dumbest to smartest
🔤 Dictionary
Try passwords from a leaked list, in order of popularity.
123456 · password · qwerty · letmein · iloveyou
💥 Pure brute force
Enumerate every string of the alphabet up to a length. Guaranteed, but slow.
a, b, c, …, aa, ab, ac, …, zz, aaa, …
🧩 Mask / hybrid
Known pattern + brute force the variable part.
Summer2024 → Summer + 4 digits
🍪 Credential stuffing
Not guessing at all — replay email/password pairs leaked from other sites.
user@a.com : Password1 → user@b.com

Most real-world "brute force" you read about is a dictionary attack with a leaked list — it's faster than enumerating the space and catches people who reuse passwords. Pure brute force is the fallback when nothing else works.

Step 5 — the defense that actually works

Rate limiting: make guessing slow

The server can't stop you from guessing — but it can refuse to answer fast. A rate limit (e.g. 5 attempts per minute per account) turns a 100-million-guess attack from seconds into decades. Watch the two panels below try the exact same attack.

Other defenses that work alongside it: account lockout after N failures, progressive delays (1s, 2s, 4s, 8s…), CAPTCHAs, and requiring MFA — which makes a correct password useless on its own.

Step 7 — why brute force is a big deal

It's never just "one account"

One cracked password is a foothold. The same attack runs against every account on the site — and because people reuse passwords, a crack on one service becomes a key to many others.

A realistic chain
1. A leaked password list from another site contains alice@example.com : Summer2023!.
2. The attacker replays it against dozens of popular sites — no guessing, no rate limit trips if they go slowly.
3. One of those sites accepts it. That account is now compromised with zero brute force involved.
4. Inside that account, the attacker finds more email addresses, more services, and repeats.

Ask yourself every time: how fast can someone try passwords against this endpoint, and what happens if they succeed?
