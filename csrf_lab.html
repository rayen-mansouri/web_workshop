CSRF — Cross-Site Request Forgery

A deep-dive, step-by-step interactive lab. Watch exactly how an attacker uses your own browser's trust to execute actions on your behalf.

Step 1 — The Core Vulnerability

How cookies force you to authenticate the attacker

When you log into a site, it gives your browser a session cookie. The browser is designed to automatically attach this cookie to every request sent to that site. It doesn't matter who triggered the request—you or a malicious site. Watch the sequence below.

Network Topology
1. Normal Login: You send your password to bank.com. The server verifies it and replies with a Session Cookie.
2. The Trap: Later, you visit evil.com. The attacker hides a request pointing to bank.com inside an image tag or hidden form.
3. The Blind Spot: The browser fires the request to bank.com. Because the destination is correct, the browser automatically attaches your cookie—even though evil.com started it.
Step 2 — The Invisible Attack

Why the attacker can't see the result (and why it doesn't matter)

This is the hardest part to understand. The attacker's page cannot read the response from the bank (blocked by the Same-Origin Policy). But the attack still works, because the server executes the action the moment it receives the request.

1. The Trigger: You load evil.com. The browser fires a hidden POST request to bank.com/transfer in the background.
2. The Execution: The server receives the request with your valid cookie. It processes the transfer, draining your balance.
3. The Asymmetry: The server replies. But the browser blocks evil.com from reading it (Same-Origin Policy). The attacker sees an error, but the money is already gone.
Step 3 — Defense 1: CSRF Tokens

The Secret Handshake

To stop the attack, the server must require a secret that the attacker doesn't have. It generates a random CSRF Token, embeds it in the legitimate HTML form, and expects it back. The attacker can forge the request, but they can't guess the token.

Token Architecture
1. Legitimate Request: You visit the form. The server generates a random secret (Token) and sends it to your browser.
2. Legitimate Submit: You submit the form. The browser sends the Token back. The server verifies it matches your session, and allows the transfer.
3. Malicious Request: The attacker's forged request still carries your cookie, but not the Token, because they can't read it from the real form. The server sees it missing and rejects it with a 403 Forbidden.
Step 4 — Defense 2: SameSite Cookies

The Browser Says "No"

Modern browsers have a built-in defense. If a cookie is marked SameSite=Strict, the browser will refuse to attach it to any request originating from a different site. The attack is stopped before it even leaves your computer. (Browsers now default to Lax, which also drops the cookie on cross-site POSTs.)

The Browser Guard
Waiting to fire cross-site request...
1. The Trigger: The attacker fires the request to bank.com. It passes through the browser.
2. The Block: The browser checks the cookie's SameSite flag. It sees the request is cross-site, so it strips the cookie.
3. The Rejection: The request arrives at bank.com empty. The server responds 401 Unauthorized. The attack fails.
